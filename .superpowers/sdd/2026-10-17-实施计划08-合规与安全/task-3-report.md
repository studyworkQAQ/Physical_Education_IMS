## ③ 加密那一层

### 3.1 产物头的形状（⚠️ 逐字节布局的**唯一所有者**是 `backup.py` 的模块 docstring；本节只报实测）

一份 1 597 440 B 的库、设口令之后：

```
产物 = pe-20261018T050906Z.db / 1597548 B
1597548 = 头 60 + 密文 1597456 + 尾 32        ← 密文 = 明文向上补到 16 的倍数**再多一个整块**（PKCS7）
产物头前 8 字节 = b'PEBACKUP'
头上写着：iterations=600000  salt=d556ad28ee84206c…  iv=43ba985b8d43de7e…
          plaintext_len=1597440  cipher_len=1597456
明文档那一份（不设口令）= 1597440 B、头 16 字节 = b'SQLite format 3\x00'
```

⚠️ **文件名与侧车两档逐字相同**（`pe-<UTC ts>.db` + `.db.sha256`，侧车都是 86 B），
「这一份是明文还是密文」由**产物头**回答、不由扩展名回答 ⇒ `restore` 两种都吃。
⚠️ 侧车算的是**产物文件本身**（头+密文+MAC），故 `write_sidecar` / `read_sidecar` /
`restore.verify_backup` 三处**一个字都没改**。

### 3.2 缺 `PE_BACKUP_KEY` 时的那一段 ⚠️（逐字，`backup.py` 真跑）

```
   形状   **明文档**（产物头是 SQLite 自己的格式串，任何 SQLite 客户端直接打开）

   ⚠️⚠️⚠️ 这一份是**明文**的：它是一个可以直接用任何 SQLite 客户端打开的
      整库副本，里面是全校学生的**出生日期、体成分、体测结果、运动处方与预警**。
      它一旦被拷进 U 盘 / 网盘 / 邮件附件，就**只**受那台机器的文件系统权限
      保护 —— 而一个 U 盘没有权限、也没有防火墙。
      ⇒ 要加密请设一个环境变量、再跑一次同一条命令：
            $env:PE_BACKUP_KEY = "<一个只有运维知道的口令，至少 8 个字符>"
            powershell -ExecutionPolicy Bypass -File backend\scripts\backup.ps1
        产物会变成一份**自描述**的加密档（AES-256-CBC + HMAC-SHA256），

        与备份**分开**的地方。
      ⚠️ 本段告示**不因任何别的环境变量而闭嘴**：$PE_BACKUP_KEY 不在，这一份就是明文的，
        而那一格必须响（而不是静默产出一份看起来一样的备份）。
```

⚠️ 退出码 **0**、产物**可用**（`restore` 吃得下、端到端绿，§4.1），⚠️ **不是** raise

### 3.3 PBKDF2 的参数与「两把钥匙不同源」的取证

| 格 | 实测值 | 谁是所有者 |
|---|---|---|
| KDF | PBKDF2-**HMAC-SHA256** | `backup.derive_keys` |
| 迭代次数（缺省） | **600 000** | `app.auth.passwords.PBKDF2_DEFAULT_ITERATIONS`（⚠️ `backup.py` 一个数都不自己写） |

### 3.4 ⚠️⚠️ 「先验 MAC」为什么承重：**绕过它**的定点取证（本波真跑）

派单逐字要求把 `backup.py:149-150` 那一格做成常驻守卫 + 定点变异。实测姿势：
拿一份**真的**加密产物、把密文中间偏移 798 788 那一个字节翻掉（`0x3c → 0xc3`），然后——

```
① 走 backup.verify_container（先验 MAC）：
   BackupError: 拒绝解密 tampered.db：HMAC-SHA256 **验不过**。⚠️ 只有两种可能，
   而它们在密码学上不可分辨：① $PE_BACKUP_KEY 里那个口令**不是**加密这一份时用的那一个；
   ② 这一份产物被改过（哪怕只改了 1 个字节…）

② **绕过** MAC、直接叫 aes_cbc.ps1 解密那一段密文（正确的 AES 钥匙 + 头上那个 IV）：
   退出码 = 0        ← ⚠️ 就是这一格
   stdout=''  stderr=''
   产物存在=True 字节=1597440
   产物头 16 字节 = b'SQLite format 3\x00'
   sqlite3 能打开它、student 行数 = 60
   前 6 行 = [(1,'周晨阳','2006-12-07'), (2,'许建国','2003-11-06'), (3,'马建国','2007-06-22'),
              (4,'赵锦程','2005-05-01'), (5,'赵婉清','2006-08-18'), (6,'赵志强','2003-10-02')]
   ⇒ ⚠️⚠️ **静默产出了一个坏库**：退出码 0、能打开、行数对、姓名与出生日期照样读得出来，
      而坏掉的那两个块就在里面（本例落在别处，故前 6 行看着完全正常 —— 那正是它最坏的地方）
```

⇒ **「必须有独立的 HMAC、而且先验」不是理论洁癖，是本机量出来的一格。**
常驻守卫：`test_a_wrong_passphrase_never_reaches_the_cipher` /
`test_tampering_with_the_ciphertext_or_with_the_mac_is_both_refused` /
`test_tampering_with_an_encrypted_product_is_refused_by_both_layers` /
`test_no_verify_skips_the_sidecar_but_never_the_hmac`；
定点变异 **M1**（把那一次 `compare_digest` 废掉）→ **红 4 条**（§6）。

⚠️ **为什么不是 AES-GCM**：实测口径**逐字住在 `backup.py` 的模块 docstring（第一格裁定）
与 `aes_cbc.ps1` 的文件头**（本机 PowerShell 5.1.26100.9711 / CLR 4.0.30319.42000 =
.NET Framework 4.x 上 `[System.Security.Cryptography.AesGcm]` 报 `Unable to find type`、
`New-Object` 同样失败）。⚠️ **本报告与 spec §13.25.2 都只指过去、不抄第二份**（派单逐字要求）。
⚠️ 那一格也正是计划 §3 预留的替代路径（「AES-CBC + 独立的 HMAC 侧车」）⇒ **方案不用再议**。

### 4.3 ⚠️⚠️ 端到端撞出来的**预存缺陷**（本波唯一一处改产品代码）

**症状**：把目标库**改坏**（不是删掉）再恢复 ⇒ 改前是**裸栈 + 退出码 1**：

```
Traceback (most recent call last):
  File "…\backend\scripts\restore.py", line 447, in restore_database
    _assert_not_in_use(db_path)                                   # 步 ②
  File "…\backend\scripts\restore.py", line 248, in _assert_not_in_use
    connection.execute("BEGIN IMMEDIATE")
sqlite3.DatabaseError: file is not a database
```

**根因（三步都读不了一个「不是数据库」的文件）**：① 步 ② 只捕
`sqlite3.OperationalError`，而 SQLite 对「文件头不对」报的是 `sqlite3.DatabaseError`；
② 步 ③ 的 `create_backup` 走 `sqlite3.backup()`，读不了它；
③ 步 ④ 的 `sqlite3_backup_init` 同样读不了一个内容是垃圾的目标。
⚠️ 而「库坏了」恰恰是恢复**最常见**的理由 ⇒ **最需要恢复的那一档恢复不了**，
而屏幕上是一段 traceback、退出码 **1**（= 「预期外的 bug」那一档，运维会以为脚本自己坏了）。
⚠️ **如实记**：这一格在 `main`（`d425d9c`）上**逐字存在**（`git show d425d9c:backend/scripts/restore.py`
比对过 `_assert_not_in_use` 全文，一个字都没差），**不是** Plan 08 引入的；
本波因为派单的端到端判据逐字点名了「把库改坏」那一档，当场量了出来。

**改后三格**（判据的唯一所有者 = 新的 `restore.is_readable_database`，⚠️ 一次恢复**只判一次**、
步 ②③ 各拿它一半，故两步不可能各看到一半）：

1. **步 ②** 放行（一个「不是数据库」的文件不可能有进程持有它的 SQLite 写事务，
   故锁检测无从谈起），⚠️ 而 `main` 把这一格**打印出来**（不是静默放行，见 §4.1 那三行）；
2. **步 ③** 的后路退化成一次**逐字节副本**（`_copy_corrupt_target_aside`，
   label `-pre-restore-corrupt`，⚠️ 形状仍落在 `BACKUP_NAME_RE` 里 ⇒ `-Keep` 认得出它、
   不会给 `backups/` 又留一个永不收缩的角落）。⚠️ 它**不能**被 `restore` 恢复
   （产物头认不出），⚠️ 而屏幕上把这一句说清楚了（§4.1）—— 它的用途是**取证**与
   交给 `sqlite3 .recover`。⚠️ 而**跳过**后路更坏：步 ④ 会把那些字节静默覆盖掉
   （一次不可逆的销毁），而屏幕上只有一句「后路 无」；
3. **步 ④** 之前把目标**清空到 0 字节**（并把 `-journal` / `-wal` / `-shm` 删掉：
   留一个属于**旧**库的 `-wal` 在旁边，下一次打开那个新库时 SQLite 会去读它）。

**⚠️⚠️ 第 3 格里还藏着第二个洞，也是实测换来的**：第一版写的是 `db_path.unlink()`，
而**首跑端到端时它炸成了一档很坏的形状** —— 恢复的自检与事后的行数复核**都**读到 60 人，
起服务那一刻文件却**不在了**，于是 `init_db` 走档 1 从零建了一个**空**库、
`/api/health` 报 **`students: 0`**（= 「恢复成功了」而库其实是空的）。
归因：Windows 上 `unlink` 一个**仍被别的进程开着句柄**的文件（杀毒实时扫描 / 索引服务 /
一个还没退干净的浏览器）会进入「**delete pending**」—— 名字还在、
而**最后一个句柄一关整个文件就消失**；`sqlite3.connect` 期间写进去的内容随它一起没了。
⇒ 改成**截断到 0 字节**（不删名字）：那一档在结构上不可能发生，而 SQLite 把
「0 字节文件」当成一个空库，`sqlite3_backup_init` 照样把它写成恢复出来的那一份。
⚠️ 那一格有守卫（下面第 5 条：一个**句柄开着**的旁观者 + 恢复仍然成功 +
句柄关掉之后文件**还在** + 三个 sidecar 都不在了），⚠️ 而定点变异 **M8**（换回 `unlink`）**红 1 条**。

**本波为这一档新增的 5 条守卫**：
① `test_a_corrupt_target_is_restored_instead_of_answering_with_a_traceback`（明文档：
`main` 回 **0**、那一行回到备份点、自检表数 **30**、输出里两格都说清楚、

② `test_a_corrupt_target_is_restored_from_an_encrypted_backup_too`（加密档同一档 +

③ `test_the_corrupt_safety_net_is_never_offered_as_a_restorable_backup`（拿它去恢复 ⇒
