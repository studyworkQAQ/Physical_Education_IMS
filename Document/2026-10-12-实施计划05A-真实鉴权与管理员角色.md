## 1. 目标与非目标

**目标**：把「请求头传身份」换成**真实鉴权** —— 首次绑定密码 → 登录 → **HttpOnly cookie 会话** → 校验 → 登出（**服务端真的失效**）；并引入 `role` 区分 `teacher` / `admin`，**管理台的写操作归管理员**。

**非目标（一律不做，但都要在 spec 里写明是已知局限）**
- ❌ 密码找回 / 邮箱短信验证 / 图形验证码 / 登录失败锁定 / 账号锁定时长
- ❌ OAuth / SSO / CAS（真实环境是统一身份认证，**原型不对接**）
- ❌ RBAC 的细粒度权限矩阵。**`role` 只影响两件事**：① 管理台的写操作要不要 `admin`；② 是否越过任教范围闸门（§4.3）。**不建权限表。**
- ❌ CSRF 的双重提交令牌（见 §3.5 —— 用 `SameSite=Lax` + 「变更类请求必须是 POST/PATCH/DELETE 且带 JSON body」两条顶住，**并把残余风险写进 spec**）
- ❌ **不动视觉**（那是 Plan 05B）。⚠️ **但登录页与注册页是本计划新建的，它们要用现有的 `tokens.css`**，不要引入第二套设计语言 —— 否则 05B 要重做两遍。

## 2. ⚠️ 三条前置决定

### 2.1 双通道过渡：请求头鉴权**不能删**

**事实**：现有 **1270 条测试**全部假设请求头身份；`smoke.mjs` 的 16 步也是。**删掉它 = 全部重写，而它们验的是业务规则、不是鉴权。**

**设计**：`app/config.py` 加 **`PE_ALLOW_HEADER_IDENTITY`**（缺省 **`"0"`**）
- `"1"` → `current_student` / `current_teacher` **先看 cookie 会话，没有就回落到请求头**（测试与开发用）
- `"0"` → **只认 cookie 会话**，缺会话一律 **401 `unauthenticated`**（生产用）
- **测试的 `conftest.py` 把它设成 `"1"`** → **1270 条一条都不用改**

⚠️ **必须有一条守卫钉住「缺省是 0」** —— 否则「生产环境忘了设、于是谁都能伪造请求头」这一档是**静默的**。守卫形状：`monkeypatch.delenv` 之后重建 app，断言匿名带 `X-Student-Id: 1` 读 `/api/students/1/home` 是 **401**。
⚠️ **`demo.ps1` 要设 `PE_ALLOW_HEADER_IDENTITY=1`**（否则演示库起来之后、前端登录页落地之前会全 401）。**这是有意的过渡态**，写进待清扫：**05A 全部完成后要把它撤掉**（因为本计划就包含前端登录页）。

### 2.2 cookie 会话**不需要改 CORS**（控制者此前那条说法过宽，在此更正）

**需求记录 §二 R2 第 3 点写的是**：「cookie 会话方案要求先把 CORS 改成显式 origin 白名单」。**那句只在跨域时成立。**
**实测事实**：`vite.config.ts` 已配 `'/api': { target: 'http://127.0.0.1:8000', changeOrigin: true }` → **浏览器看到的是同源**（`localhost:5173` 发请求给 `localhost:5173/api/...`，由 Vite 转发）。**故 cookie 是第一方的，`SameSite=Lax` 就够，CORS 一行都不用动。**
⚠️ **但要在 spec §13 里写明生产部署的那一档**：若前端与后端**不同源**部署，则需要 ① `allow_origins` 改成显式白名单（不能是 `*`）② `allow_credentials=True` ③ cookie 加 `Secure` 且 `SameSite=None`。**原型按同源部署（`vite build` 的产物由后端或同一个反代托管），故不触发这一档。**

### 2.3 采纳 `e5efe6e` 的 5 条工程决定（与产品口径无关）

1. **密码哈希用标准库 `hashlib.pbkdf2_hmac`，不引新依赖。** ⚠️ **Plan 01–04 全程零新增依赖**（`pyproject.toml` 从 Plan 01 起没动过，且它有 sha256 指纹测试）。**用户选了 cookie，故连 `pyjwt` 都不需要**（那是 Bearer 方案的依赖）→ **本计划的新增依赖数是 0**。
2. **存储格式是自描述串**：`pbkdf2_sha256$<iterations>$<salt_b64>$<hash_b64>`。**自描述是为了将来能换算式而不做数据迁移**（换成 argon2 时旧串仍能被识别与校验）。**校验函数必须先解析算式名与迭代次数、再用它们重算**，不要写死。
3. **迭代次数必须可配**（`PBKDF2_ITERATIONS`，生产缺省 **600 000** = OWASP 2023 对 PBKDF2-SHA256 的建议值；**测试里设成 1 000** —— 否则每条碰密码的测试都要 0.3 秒，套件会从 2.3 分钟变成半小时）。⚠️ **要有一条守卫钉住「生产缺省 ≥ 600 000」**，否则「测试把它调低了、忘了调回来」是静默的。
4. **比较必须用 `hmac.compare_digest`**（定时攻击）。⚠️ **这一条要有变异自证**：把它换成 `==`，守卫要红。
5. **`bind` 的竞态**：两个请求同时绑定同一个学号。**在 UPDATE 的 WHERE 里带上 `password_hash IS NULL`**，据影响行数判 409 —— **不要靠「读出来是 NULL 就写」**（那是 check-then-act，两个都能过）。

**⚠️ 不采纳它的第 6 条**（`teacher` 表加 `role` 列的**同时**把管理台设为「同权」）—— 用户裁定是「接管」，故 §4.2 的做法不同。

### 2.4 ⚠️ 为什么 05A 必须先于 05B

**`adoptFromUrl()`（`stores/identity.ts` 的深链接身份，`?student=4` / `?teacher=T0001`）是 Task 2/3/5 全部 DOM 取证的入口。** 05A 要把它降级成「仅 `PE_ALLOW_HEADER_IDENTITY=1` 时可用」，**`smoke.mjs` 第 14 步的 13 条路由取证必须改成「先登录拿到 cookie、再带着 cookie 请求」**。
**若先做 05B（视觉重构），它的取证会在 05A 落地时全部作废、要重做一遍。** 故顺序是硬的。

## 3. 后端

### 3.1 Schema 改动（⚠️ 5 列 + 1 张新表 → 表数 25 → 26）

```python
# student（加 2 列）
password_hash: Mapped[str | None] = mapped_column(String(255))   # NULL = 未绑定
password_bound_at: Mapped[dt.datetime | None] = mapped_column(DateTime)

# teacher（加 3 列）
role: Mapped[str] = mapped_column(String(16), default="teacher")  # ∈ {"teacher", "admin"}
password_hash: Mapped[str | None] = mapped_column(String(255))
password_bound_at: Mapped[dt.datetime | None] = mapped_column(DateTime)

# user_session（新表，⚠️ 服务端会话，见 §3.4）
id: Mapped[str] = mapped_column(String(64), primary_key=True)      # secrets.token_urlsafe(48)
kind: Mapped[str] = mapped_column(String(16))                      # ∈ {"student", "teacher"}
subject_id: Mapped[int]                                            # student.id 或 teacher.id
role: Mapped[str] = mapped_column(String(16))                      # 冗余存一份，见下面的 ⚠️
created_at / expires_at / last_seen_at: DateTime
revoked_at: Mapped[dt.datetime | None]                             # 登出 = 写这一列
```

⚠️ **`role` 在 `user_session` 里冗余存一份的理由与代价**：不冗余就要每次请求都 JOIN `teacher` 表；冗余了则「管理员被降权成教师」不会立刻生效（要等他重新登录）。**控制者裁定：冗余，并在 spec 里写明这个代价**（原型可接受，且降权是极罕见操作）。⚠️ **若你认为该 JOIN，顶回来。**

⚠️ **`user_session.subject_id` 刻意不建外键** —— 它要同时指向 `student.id` 与 `teacher.id`，**多态外键在 SQL 里不存在**（`e5efe6e` 为此论证过「不建多态凭据表」，但它的方案是把凭据放进两张表，故没遇到会话表这个问题）。**代价：删学生不会级联删他的会话** → **故 `on_delete` 那一档要处理**：`_child_tables` 探测不到它，删学生会留下孤儿会话行。**处置：登录时校验「subject 还在不在册」，不在就当场吊销**（并把这条写进守卫）。⚠️ **这是本计划最容易漏的一格。**

⚠️ **连带**：`_MODELS_PUBLIC_BASELINE` **33 → ?**（新增 `UserSession` 等公开名）；`models/__init__.py` 的 `__all__` 要加；**架构守卫的两条下界断言**（`len(real_py) >= 40`、`len(cases) >= 22` 之类）都是 `>=` 故不会红，但**要实测确认**；**`init_db` 的 `create_all` 会建新表**（⚠️ 而 `pe_demo.db` 是已存在的库 → **`create_all` 对已存在的表原样跳过，不会给 `student`/`teacher` 补那 5 个新列** → **`demo.ps1` 的第一步本来就是「删旧演示库」，故它会自己解决**；但**任何手工留下的旧库都会 500**，写进 spec §13 的警告）。

### 3.2 绑定端点（「名册已存在 + 首次绑定密码」）

| 端点 | 身份 | 验身材料 | 关键错误 |
|---|---|---|---|
| `POST /api/auth/students/bind` | **匿名** | **学号 `student_no` + 出生日期 `birth_date` + 新密码** | 学号不在册 **403 `forbidden`**；出生日期不符 **403 `forbidden`**（⚠️ **与「不在册」同一个 code + 同一句 message，不给攻击者区分信号**）；已绑定过 **409 `password_already_bound`**；弱口令 **422 `unprocessable_value`** |
| `POST /api/auth/teachers/bind` | **匿名** | **工号 `staff_no` + 姓名 `name` + 新密码** | 同上 |

**⚠️ 学生的「出生日期」是控制者按 `e5efe6e` 记录的裁定采用的**（用户本次只说了「名册已存在 + 首次绑定密码」，没说用什么验身）。**理由**：`student` 表实测有 `birth_date` 列（Plan 01 建的，`GET /api/students` 今天就匿名返回它 —— 终审指出过这一点）。⚠️ **这构成一个真实的安全权衡：验身材料本身是匿名可读的** → **故原型可接受、但必须写进 spec 的已知局限**，且 **Plan 05A 收尾时要重新裁定那 48 个匿名 GET**（见 §6）。
**⚠️ 教师的「工号 + 姓名」是控制者的假设**（用户只裁定了学生）。理由：教师行由管理员创建，管理员可以把工号与姓名告给他。⚠️ **`teacher` 表是否有 `name` 列请实现者实测**；若没有，用别的在册字段并**顶回来**。

### 3.3 登录 / 登出 / 我是谁

| 端点 | 身份 | 语义 |
|---|---|---|
| `POST /api/auth/login` | **匿名** | `kind`（`student`/`teacher`）+ 学号或工号 + 密码 → **`Set-Cookie`** + 响应体回 `{kind, id, name, role}` |
| `POST /api/auth/logout` | **cookie 会话** | **吊销会话行**（写 `revoked_at`）+ **`Set-Cookie` 过期** → 204 |
| `GET /api/auth/me` | **cookie 会话** | 我是谁：`kind` / `id` / `name` / `role`（+ 教师的 `staff_no`、学生的 `student_no`） |

**登录失败的两档必须区分**：未绑定 **403 `password_not_bound`**（用户该去注册）vs 密码错 **401 `invalid_credentials`**（该重输）。⚠️ **这确实泄露了「这个学号在不在册」** —— **控制者裁定：接受**，因为①原型不做防枚举②绑定流程本身就需要这个信号③`GET /api/students` 今天就匿名返回全部 60 人。**写进 spec 的已知局限。**

**⚠️ 本计划不做 refresh 令牌** —— cookie 会话用**滑动过期**（每次请求把 `expires_at` 往后推，`last_seen_at` 更新），故不需要「两种令牌」那一套。**这是 cookie 方案相对 Bearer 的一个实际简化，要在 spec 里写明。**

### 3.4 会话存储：**服务端表**，不是签名 cookie

**两个选项**：(a) 服务端 `user_session` 表 + cookie 里只放一个不透明 id；(b) HMAC 签名的自包含 cookie（无状态）。
**控制者裁定选 (a)**，三条理由：① **登出是真的失效**（(b) 的登出只是客户端丢弃，被偷的 cookie 在过期前仍有效）—— 而用户说现状「有点太粗糙了」，**「登出登不掉」正是那一类粗糙**；② 只多一张表，代价可控；③ 与本仓「一切承重的事实都落在库里、可追溯」的既有纪律一致（`daily_sync_run` / `cleaning_log` 都是这个形状）。
**代价（如实记）**：**过期行不会自己消失** → 原型不做清理任务，但**要有一条守卫钉住「过期或被吊销的会话不能用」**，并在待清扫里记「生产需要一个清理任务」。
**cookie 参数**：`HttpOnly=True`（**JS 读不到，故 XSS 拿不走**）、`SameSite=Lax`、`Path=/`、`Secure` 仅在 `PE_ENV=production` 时开、**不设 `Domain`**（默认宿主限定）。**cookie 名 `pe_session`**。⚠️ **`Max-Age` 要与 `expires_at` 同源**（不要一个写 7200 一个写 86400）。

### 3.5 CSRF：用两条顶住，不做双重提交令牌

**残余风险如实写进 spec**：`SameSite=Lax` 挡住的是**跨站的 POST**（Lax 下跨站请求不带 cookie），**但它不挡同站的子域、也不挡用户自己被诱导在本站点上发请求**。**本计划加第二条**：所有变更类端点（POST/PATCH/DELETE）**要求 `Content-Type: application/json`** —— 而**跨域的 JSON POST 会触发 CORS 预检**，预检在 `allow_origins=["*"]` 且**不带** `allow_credentials` 时**拿不到允许携带凭据的响应**，故被挡。⚠️ **这条论证依赖 §2.2 的「同源部署」前提** —— **若生产改成跨源 + `allow_credentials=True`，这条论证就失效，必须补双重提交令牌**。**把这句话逐字写进 spec。**

### 3.6 授权：`role` 影响的两件事

1. **管理台的写操作归管理员**（用户裁定「接管」）：`app/api/crud.py` 的 `build_crud_router(require_teacher=…)` → **改成 `require_admin=…`**，9 个可写资源的 POST/PATCH/DELETE **从「教师可写」变成「仅管理员可写」**。⚠️ **这会改掉 fix 波 1 那条遍历型守卫的语义**（`test_every_writable_resource_rejects_an_anonymous_mutation`）→ **要扩成三拍：匿名 401 / 教师 403 / 管理员 201**。⚠️ **那条全仓级断言（钉住「挂 security 的操作数 = 46」）也会红** → 按硬规矩 #88 先跑全量收进来。
2. **管理员越过任教范围闸门，教师保留**（控制者的推论，⚠️ **用户未裁定，需要实现者复核并在报告里确认**）：`require_teaches_section` / `require_teaches_student` 今天要求「这个教师真的教这个班/这个学生」。**管理员（教务干事）通常不带任何班** → 若不放行，`role='admin'` 就只是个标签、**这个角色没有意义**。**故：`role == "admin"` 时越过这道闸门；`role == "teacher"` 时保留。**

**⚠️ 教师自己的那些特例端点怎么办**（`open-rpe` / `rpe-token` / `mini-tests/batch` / `alerts/{id}/handle` / `teacher/students/*`）：**改成「教师或管理员都可以」**（新增一个 `require_staff` 依赖 = `role in {"teacher","admin"}`）。**理由**：管理员接管的是**管理台**，不是把教师赶出课堂功能。⚠️ **这一条用户没裁定，若你认为管理员不该碰课堂功能，顶回来。**

## 4. 前端

### 4.1 新增：登录页与注册（绑定）页

**⚠️ 用现有的 `tokens.css` 与 `lane.css`，不要引入第二套设计语言**（Plan 05B 会整体换肤，届时这两个页面跟着一起换）。

- **`/login`**：选身份（学生 / 教师 / **管理员就是教师里 `role='admin'` 的那些，故登录表单不单独列管理员** —— ⚠️ **但登录后要按 `role` 跳到不同的首页**：学生 → `/s/home`、教师 → `/t/dashboard`、管理员 → `/admin`）。
- **`/bind`**（首次绑定密码）：学生填「学号 + 出生日期 + 新密码 + 确认」；教师填「工号 + 姓名 + 新密码 + 确认」。**⚠️ 弱口令（< 8 位）要在前端就拦一道**，但**后端的 422 仍是唯一权威**（前端那道只是省一次往返）。
- ⚠️ **`fetch` 必须带 `credentials: 'same-origin'`**（同源下这是默认值，但**显式写出来**，否则 §2.2 的那个「同源」前提被破坏时不会有任何提示）。⚠️ **`client.ts` 今天刻意不设 `credentials`**（Global Constraints 第 1 条）→ **本计划要改它，并把那条约束的注释改成「同源部署下用 `same-origin`；跨源部署要连 CORS 一起改」**。

### 4.2 路由守卫

- `/s/*` → 要学生会话；`/t/*` → 要 `role ∈ {teacher, admin}`；`/admin/*` → **要 `role == 'admin'`**
- 未登录 → 跳 `/login?next=<原路径>`；角色不符 → 跳自己的首页 + 一条说明（**不要只显示空白**）
- ⚠️ **`admin` 访问 `/t/*` 是允许的**（§3.6 第 2 条）

### 4.3 ⚠️ `IdentitySwitcher` 与 `adoptFromUrl()` 的处置（本计划最容易漏的一格）

**事实**：`adoptFromUrl()` 是 Task 2/3/5 **全部 DOM 取证的入口**（`?student=4` / `?teacher=T0001`）。
**裁定**：**保留，但降级成开发工具** —— 仅在 `import.meta.env.DEV` 为真**且**后端 `PE_ALLOW_HEADER_IDENTITY=1` 时生效；**生产构建里它必须不存在**（用 `import.meta.env.DEV` 做条件，Vite 会在 build 时把那一支摇掉 —— **要有一条守卫证明摇掉了**：`npm run build` 之后 grep `dist/` 里不含 `adoptFromUrl`）。
**`IdentitySwitcher.vue`** → **换成一个「当前身份 + 登出按钮」的组件**（开发模式下额外保留切换能力）。
⚠️ **`smoke.mjs` 第 14 步的 13 条路由取证必须改成「先 `POST /api/auth/login` 拿到 cookie、再带着 cookie 打开页面」** —— 而**无头浏览器的 `--dump-dom` 不带 cookie jar**，故**要改用一个能设 cookie 的姿势**（例如 `--headless=new` + 一段注入脚本，或改用 Node 的 `fetch` 拿到 HTML 后…⚠️ **不行，那是 SSR 的形状，本项目是 CSR**）。**控制者倾向：`smoke.mjs` 第 14 步改用 Playwright/Puppeteer** —— ⚠️ **那是新依赖**，与「零新增依赖」的口径冲突，**但那是前端 devDependency、不是后端生产依赖，故可接受**。**若你有不加依赖的办法，顶回来。**
